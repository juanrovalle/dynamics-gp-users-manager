Instalación y pruebas, paso a paso

1. Antes de comenzar

Primero realiza estas pruebas sobre una copia aislada de GP, con cuentas de prueba y sin operaciones de negocio en curso. Al aprobar los resultados, repite la instalación en el ambiente acordado con el cliente.

Qué hace el retiro: elimina registros de la sesión seleccionada en GP y Dexterity. No cierra ordenadamente la ventana de GP ni cancela de forma controlada el trabajo del usuario. Una sesión activa puede verse afectada. No pruebes retiros con usuarios que estén contabilizando documentos reales.

Prepara identidades existentes en SQL Server

  1. TI utiliza una identidad sysadmin para instalar los objetos SQL. No es la cuenta diaria del encargado de GP.
  2. Crea o identifica un login Windows, grupo Windows o login SQL para el encargado de GP. En el asistente recibirá el rol Administrador del producto. Para consulta utiliza Lector.
  3. Crea o identifica un login individual separado, por ejemplo GPUM_Engine, para el motor. No debe ser sysadmin ni la identidad instaladora. No uses un grupo Windows para este login.
  4. Identifica un propietario administrador para el job de SQL Agent. El asistente exige elegirlo explícitamente. Ese propietario restaura permisos de tempdb tras reinicios y luego ejecuta el control como el login restringido del motor.

Si hace falta crear un login, TI puede hacerlo en SSMS → Seguridad → Inicios de sesión → Nuevo inicio de sesión. Usa autenticación Windows cuando corresponda; para SQL aplica la política de contraseñas del cliente. No otorgues sysadmin a la cuenta operadora ni al motor. No es necesario crear usuarios de GP desde esta aplicación.

Las contraseñas SQL introducidas en la consola permanecen únicamente durante la sesión. No se incluyen en el perfil, diagnóstico ni comando del job. Un login SQL de operación requiere que el servidor admita autenticación SQL.

2. Instalar la consola en Windows

  1. Copia Setup.exe al PC de administración. No hace falta instalarlo en cada equipo que utiliza GP.
  2. Comprueba la versión y el SHA-256 entregado con el paquete. Si la entrega está firmada, revisa Propiedades → Firmas digitales y el editor. El paquete generado aquí no tiene firma digital; no confundas eso con una firma Microsoft. TI debe aprobar su origen según su política.
  3. Ejecuta Setup, selecciona idioma, revisa la licencia MIT, confirma carpeta e instala. Se solicitarán permisos de administrador de Windows para copiar la aplicación.
  4. Abre GP Users Manager desde Inicio. También aparece un acceso a esta guía. El runtime se incluye en el paquete y la instalación no descarga dependencias.
  5. Para ver la interfaz sin conectar un servidor, pulsa Ver demostración. Los datos son ficticios y no se realizan cambios.

Cuando lo instales en Windows Server

  1. Confirma en Server Manager / información del sistema que estás usando Desktop Experience, no Server Core. El instalador verifica el tipo y el build antes de copiar archivos.
  2. Instala una sola consola en el servidor administrativo elegido. Puedes utilizar RDP; no necesitas dejar la sesión abierta para mantener el control de cupos.
  3. Para SQL en el mismo servidor usa su nombre real, por ejemplo SRV-GP o SRV-GP\INSTANCIA; para SQL remoto utiliza el nombre/puerto acordado con TI. No cambies la base GP.
  4. TI debe comprobar conectividad y certificado. Setup no modifica firewall, RDP, servicios de SQL, IIS ni roles de Windows.
  5. La consola corre con el usuario que la abre. Las credenciales de instalación SQL se solicitan aparte en el asistente; no se guardan.
Setup instala archivos en Windows. La instalación de tablas, procedimientos, permisos y job se realiza después, desde el Asistente de instalación / actualización. Son dos etapas distintas.

3. Completar el asistente de TI

Paso 1 — Conectar

  1. Desde la pantalla inicial abre Asistente de instalación / actualización.
  2. Indica servidor/instancia, autenticación Windows o login SQL administrador. Escribe la contraseña solo si corresponde.
  3. Pulsa Listar bases. Selecciona la base de sistema GP y escribe o selecciona la base del gestor.
  4. Si existe un certificado SQL confiable, deja desmarcada la opción de confiar explícitamente. Úsala únicamente por decisión de TI si su entorno requiere aceptar el certificado del servidor.
  5. Pulsa Continuar.

Resultado esperado: se muestran las verificaciones del servidor seleccionado; aún no se han creado los objetos del gestor.

Paso 2 — Verificar

  1. Comprueba permisos de instalación, versión SQL, Agent, tablas GP/Dexterity, esquema SY30000 y base destino.
  2. Si una comprobación falla, corrige el motivo con TI y utiliza Repetir verificaciones. No continúes con errores.
  3. En Job que se conservará, selecciona el existente o Crear el job del producto. Si hay jobs anteriores debes elegir explícitamente. Un job de varios pasos no se reescribe: crea el nuevo y confirma luego que el anterior se deshabilite.
  4. Revisa también con TI jobs personalizados que llamen al procedimiento mediante otro wrapper: la detección busca referencias directas a SP_LOGOUTGPUSER_BY_QUOTE.

Resultado esperado: todas las verificaciones correctas y una selección de job inequívoca. Los jobs no seleccionados todavía no se deshabilitan.

Paso 3 — Instalar o actualizar

  1. Verifica nuevamente servidor y bases. Confirma fuera del asistente que existe el respaldo necesario.
  2. Pulsa Instalar / actualizar objetos y espera el resultado.
  3. Continúa solo cuando aparezca que los objetos quedaron instalados.

Resultado esperado: una nueva instalación permanece pausada. En una actualización se conservan departamentos, usuarios, configuración y políticas. No se borran duplicados de datos para “arreglar” una migración; si se detectan datos inválidos, se requiere intervención de TI. Una falla al crear objetos puede dejar una base nueva vacía; no borres bases existentes para reintentar.

Paso 4 — Configurar departamentos, usuarios y permisos

  1. Pulsa Abrir departamentos, cupos y registro comercial. Esta ventana usa temporalmente la sesión de TI.
  2. En Departamentos, pulsa Nuevo, escribe nombre y cupo, marca si estará habilitado y guarda. Cupo 0 significa que cualquier sesión asignada excederá el límite; no significa ilimitado.
  3. En Usuarios, busca una cuenta ya existente en GP, selecciónala, elige su departamento y pulsa Guardar asignación. Repite con las cuentas acordadas. Quitar una asignación no elimina la cuenta GP.
  4. En Configuración, revisa la política de protección de actividad y los avisos nativos. Registra cliente, contacto, compra y mantenimiento. La fecha de mantenimiento no bloquea el producto. Guarda y cierra esta ventana para volver al asistente.
  5. Selecciona una identidad de operación y su rol; pulsa Agregar identidad por cada cuenta o grupo.
  6. Selecciona el login restringido del motor y el propietario administrador del job. Pulsa Aplicar permisos.

Resultado esperado: cuentas y cupos guardados; permisos aplicados a identidades existentes. El asistente agrega permisos: quitar una identidad de la lista no revoca permisos anteriores. TI debe revisar o revocar permisos previos por separado.

Paso 5 — Comprobar sin retirar

  1. Revisa la lista de candidatos. Esta consulta no retira sesiones.
  2. Escribe explícitamente el usuario GP destinatario y selecciona su compañía.
  3. Con ese usuario conectado a GP, pulsa Enviar mensaje de prueba y confirma el destinatario.
  4. Observa el cliente GP. Marca Confirmé que el usuario recibió el aviso dentro de GP únicamente si realmente apareció. No basta una fila en Historial.
  5. Continúa. Si los avisos están habilitados, el asistente exige envío y confirmación.

Resultado esperado: aviso mostrado en el cliente correcto, sin retirar su sesión. La aplicación no puede confirmar automáticamente lectura ni entrega.

Paso 6 — Activar o finalizar en pausa

  1. Revisa el job elegido, las identidades y los nombres de los jobs que se deshabilitarán.
  2. Confirma la política de retiro y selección de jobs.
  3. Para dejarlo listo sin retiros, usa Finalizar con automatización pausada. Para empezar el control, usa Activar y finalizar.
  4. Cierra la sesión de TI. Conecta desde la pantalla principal con la identidad de operación, indicando las mismas bases.

Resultado esperado: existe un único job seleccionado para ejecutar el control; los otros detectados quedan deshabilitados, no eliminados. El job puede estar habilitado mientras el gestor está pausado: en ese caso solo registra el estado PAUSED y no retira.

El control está programado cada minuto. Tras activar, una sesión elegible puede retirarse en la siguiente ejecución. No actives hasta acordar la política y preparar usuarios de prueba.

5. Actualizar una instalación existente

De 3.0.0 a 3.0.1: esta actualización solo amplía los destinos Windows del instalador. Cierra la consola, ejecuta el nuevo Setup sobre la misma carpeta y vuelve a conectar. El esquema SQL sigue en versión 3; no hace falta repetir migraciones ni reconfigurar el job. Los pasos siguientes se aplican cuando necesitas instalar o actualizar los objetos SQL, por ejemplo desde el esquema original.
  1. Registra versión, departamentos, cupos, asignaciones, políticas, estado activo/pausado y jobs existentes. TI realiza backups y acuerda una ventana de mantenimiento.
  2. Cierra las consolas e instala el nuevo Setup sobre la misma carpeta.
  3. Abre el asistente con la cuenta de TI. Selecciona la misma base del gestor y la misma base GP. No crees otra base para “actualizar”.
  4. Revisa jobs y selecciona explícitamente el que conservarás. El asistente no debe reescribir un job de múltiples pasos; selecciona crear el del producto en ese caso.
  5. Ejecuta migraciones, revisa datos conservados, selecciona identidades y prueba avisos.
  6. Finaliza con el estado acordado. Si antes estaba pausado y debe seguir así, utiliza Finalizar con automatización pausada; no pulses Activar por rutina.
  7. Repite comprobaciones de operación, permisos y ejecución independiente de la consola.

El instalador rechaza una base con esquema más nuevo y no cambia el enlace a otras bases GP/Dexterity. No incluye migración inversa de esquema. Ante una falla, conserva el diagnóstico y usa el procedimiento de recuperación de TI; no borres datos para reinstalar.

6. Desinstalar sin sorpresas

Desinstalar la consola no detiene el job ni borra bases. El desinstalador muestra una advertencia. Conserva también el perfil local de conexión sin contraseña.

  1. Si solo retiras la consola de un PC, desinstala desde Configuración de Windows → Aplicaciones. El motor seguirá funcionando.
  2. Si deseas detener el producto completo, primero pulsa Pausar automatización y verifica una ejecución PAUSED.
  3. TI puede deshabilitar el job seleccionado después de verificar la pausa. Conserva respaldo e historial según las políticas del cliente.
  4. Desinstala la consola. Cualquier eliminación definitiva de bases/objetos requiere una decisión aparte del DBA; Setup no la realiza.

7. Diagnóstico y problemas frecuentes

ProblemaQué revisar
No conectaServidor/instancia/puerto, firewall, red, modo de autenticación, login habilitado y certificado. No envíes contraseñas por soporte.
Agent no pasa verificaciónTI comprueba servicio, edición de SQL y permisos. La consola no instala SQL Server ni inicia servicios automáticamente.
Faltan DEX_SESSION / DEX_LOCKComprueba que el GP de prueba esté preparado y se haya abierto un cliente tras reiniciar SQL. No crees tablas Dexterity inventadas en producción.
Esquema de mensajes incompatibleRevisa build GP, SY30000, tipos/longitudes/defaults y personalizaciones. No fuerces una inserción ignorando la verificación.
No permite reactivarSi activaste avisos nuevos, completa envío y confirmación desde el asistente de TI. Revisa también el permiso de administrador del producto.
Sin ejecución recienteEstado del job, calendario, historial de errores, permisos, Agent y SQL. El texto no identifica automáticamente la causa.
No se puede guardar un cambioRol de operación, límites válidos y conflicto de revisión. Recarga para no sobrescribir cambios de otro administrador.
Mensaje encolado pero no visibleUsuario, compañía, cliente GP y momento posterior al retiro. No marcarlo como leído basándose en SQL.

Desde Configuración → Exportar diagnóstico, guarda el JSON para soporte. Incluye versión, base/servidor y estado del motor; excluye contraseña, registro comercial y textos libres de auditoría. Revisa el archivo antes de compartirlo: los nombres de servidor/base siguen siendo información interna.

Adjunta versión del paquete, builds SQL/GP, paso que falló, fecha/hora UTC y captura del error sin secretos. Para problemas del motor, TI revisa también el historial del job y el Historial de la consola.

El registro comercial no activa ni desactiva el software. La versión adquirida sigue funcionando sin renovar mantenimiento. Se conserva la licencia MIT del repositorio.
