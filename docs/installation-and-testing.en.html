PRODUCT GUIDE · VERSION 4.0.0

Dynamics GP UserOps
Step-by-step installation and testing

IT installs the product and prepares the accounts. The GP administrator manages departments, quotas and assignments in the console. SQL Server Agent enforces quotas even when the console is closed.

1. Before you begin

First run these tests against an isolated copy of GP, using test accounts with no live business operations in progress. After the results are accepted, repeat the installation in the environment agreed with the customer.

What session removal does: it deletes the selected session's GP and Dexterity records. It does not gracefully close the GP window or safely cancel the user's work. An active session can be affected. Do not test removal with users posting real business documents.

Prepare existing SQL Server identities

  1. IT uses a sysadmin identity to install SQL objects. This is not the GP administrator's daily account.
  2. Create or identify a Windows login, Windows group or SQL login for the GP administrator. Assign the product's Administrator role in the wizard. Use Reader for read-only access.
  3. Create or identify a separate individual engine login, such as UserOps_Engine. It must not be sysadmin or the installation identity. Do not use a Windows group for this login.
  4. Identify an administrative owner for the SQL Agent job. The wizard requires an explicit selection. That owner restores tempdb permissions after restarts, then runs quota enforcement as the restricted engine login.

If a login is needed, IT can create it in SSMS → Security → Logins → New Login. Use Windows authentication where appropriate; apply the customer's password policy to SQL accounts. Do not grant sysadmin to the operator or engine login. This application does not create GP users.

SQL passwords entered in the console remain only for the current session. They are not included in the saved profile, diagnostic export or job command. A SQL-authenticated operating login requires the server to allow SQL authentication.

2. Install the Windows console

  1. Copy Setup.exe to the administration computer. It does not need to be installed on every GP workstation.
  2. Check the version and SHA-256 supplied with the package. If the delivery is signed, check Properties → Digital Signatures and the publisher. The package generated here is unsigned; do not mistake it for a Microsoft-signed product. IT must approve its origin under the customer's policy.
  3. Run Setup, choose a language, review the MIT license, confirm the folder and install. Windows administrator elevation is required to copy the application.
  4. Open Dynamics GP UserOps from Start. Shortcuts to both language guides are included. The runtime is bundled; installation does not download dependencies.
  5. To view the interface without a server connection, click View demo. It uses fictitious data and makes no changes.

When installing on Windows Server

  1. Use Server Manager / system information to confirm Desktop Experience rather than Server Core. The installer checks the installation type and build before copying application files.
  2. Install one console on the chosen administration server. RDP is acceptable; the interactive session does not need to remain open for quota enforcement.
  3. For SQL on the same server, use its actual name, such as SRV-GP or SRV-GP\INSTANCE. For remote SQL, use the host/port agreed with IT. Do not change the GP database.
  4. IT must verify connectivity and the certificate. Setup does not modify the firewall, RDP, SQL services, IIS or Windows roles.
  5. The console runs as the user who opens it. SQL installation credentials are requested separately in the wizard and are not saved.
Setup installs Windows files. Tables, procedures, permissions, and the job are installed afterward through Setup / upgrade wizard. These are two separate stages.

3. Complete the IT wizard

Step 1 — Connect

  1. On the initial screen, open Setup / upgrade wizard.
  2. Enter the server/instance and choose Windows authentication or an administrative SQL login. Enter a password only when required.
  3. Click List databases. Select the GP system database and enter or select the UserOps database.
  4. If SQL has a trusted certificate, leave the explicit certificate-trust option unchecked. Enable it only by IT's decision when that environment requires accepting the server certificate.
  5. Click Continue.

Expected result: checks for the selected server appear; no manager objects have been created yet.

Step 2 — Verify

  1. Check installation permissions, SQL version, Agent, GP/Dexterity tables, the SY30000 schema and destination database.
  2. If a check fails, resolve its cause with IT and use Run verification again. Do not proceed with errors.
  3. Under Job to retain, select an existing job or Create the Dynamics GP UserOps job. Existing jobs require an explicit choice. A multi-step job is not rewritten: create a new product job and later confirm that the previous one will be disabled.
  4. Have IT also review custom jobs that call the procedure indirectly through a wrapper. Detection looks for direct references to SP_LOGOUTGPUSER_BY_QUOTE.

Expected result: all checks pass and exactly one job selection is agreed. Unselected jobs have not been disabled yet.

Step 3 — Install

  1. Recheck the server and databases. Confirm outside the wizard that the required backup exists.
  2. Click Install / upgrade objects and wait for the result.
  3. Continue only when the wizard reports that the objects were installed.

Expected result: a new installation remains paused. An upgrade preserves departments, users, settings and policies. Duplicate data is not deleted to “fix” a migration; invalid existing data requires IT intervention. An object-creation failure can leave a new empty database. Do not delete existing databases to retry.

Step 4 — Configure

  1. Click Open departments, quotas, and customer registration. This window temporarily uses the IT session.
  2. In Departments, click New, enter the name and quota, choose whether it is enabled, and select Save department. A quota of 0 means any assigned session exceeds the limit; it does not mean unlimited.
  3. In Users, find an existing GP account, select it and its department, then click Save assignment. Repeat for the agreed accounts. Removing an assignment does not delete the GP account.
  4. In Settings, review activity protection and native notifications. Enter customer, contact, purchase and maintenance information. The maintenance date does not lock the product. Save and close this window to return to the wizard.
  5. Select an operating identity and its role; click Add identity for each account or group.
  6. Select the restricted engine login and administrative job owner. Click Apply permissions.

Expected result: quotas and assignments are saved, and permissions are applied to existing identities. The wizard adds permissions: removing an identity from its selection does not revoke previous permissions. IT must review or revoke earlier permissions separately.

Step 5 — Test

  1. Review the candidate list. This query does not remove sessions.
  2. Explicitly enter the GP recipient username and select the company.
  3. With that user connected to GP, click Send test message and confirm the recipient.
  4. Observe the GP client. Check I confirmed that the user received the message in GP only if the message actually appeared. A row in Activity is not sufficient.
  5. Continue. When native notifications are enabled, the wizard requires a test send and confirmation.

Expected result: the correct GP client displays the message without its session being removed. The application cannot automatically confirm delivery or reading.

Step 6 — Activate

  1. Review the selected job, identities and names of the jobs that will be disabled.
  2. Confirm the removal policy and job selection.
  3. To finish without enabling removals, choose Finish with automation paused. To start enforcement, choose Activate and finish.
  4. Close the IT session. Connect on the main screen with the operating identity, using the same databases.

Expected result: one selected job runs quota enforcement; the other detected jobs are disabled, not deleted. The job may be enabled while the manager is paused: it then records PAUSED without removing sessions.

The job is scheduled every minute. After activation, an eligible session may be removed on the next run. Do not activate until the policy is agreed and test users are ready.

Critical check: notifications after removal

QUEUED_GP means the native row was inserted, not that GP displayed it. Record the delay, whether the client was busy, what happened after reconnection and the receiving user/company. If no message appears after removal, do not accept that combination. Work with GP support to determine whether notification before removal and a grace period are needed. That alternative has not been implemented automatically.

Additional Windows Server test

Install from a local or RDP desktop session. Check the local and remote SQL connections that the customer will use. Close the console and sign out of RDP; observe from another computer that the job keeps running and recording executions. Also verify that Setup rejects Server Core without installing the application. Record results separately for 2016, 2019, 2022 and 2025; do not extrapolate Windows 11 results to Server.

Checks already performed during development

C# compilation, local logic/resource/T-SQL syntax checks and screen rendering with fictitious data were verified. These checks are not equivalent to running the acceptance tests above. No deployment against a real SQL Server/GP environment or clean Windows installation was performed on this development machine.

5. Upgrade an existing installation

From GP Users Manager 3.x to Dynamics GP UserOps 4.0.0: run Setup interactively. It removes only the legacy Windows console, installs the new product identity, and keeps the existing SQL database and Agent jobs running. First launch copies the password-free profile into the new LocalAppData folder and retains the original copy. Schema migration 4 changes branded metadata and the test message without changing quotas or job policy.
  1. Record version, departments, quotas, assignments, policies, active/paused state and existing jobs. IT makes backups and agrees a maintenance window.
  2. Close the GP Users Manager 3.x console and run Dynamics GP UserOps Setup interactively. Confirm the legacy-console replacement.
  3. Open the wizard with the IT account. Select the same manager database and the same GP database. Do not create another database as an “upgrade.”
  4. Review jobs and explicitly select the one to keep. The wizard should not rewrite a multi-step job; choose creation of the product job in that case.
  5. Run migrations, review preserved data, select identities and test messages.
  6. Finish in the agreed state. If it was paused and must remain so, choose Finish with automation paused; do not activate by habit.
  7. Repeat checks for operation, permissions and execution with the console closed.

The installer rejects a newer database schema and does not change the binding to other GP/Dexterity databases. No reverse-schema migration is included. On failure, keep diagnostics and use IT's recovery procedure; do not delete data to reinstall.

6. Uninstall without surprises

Uninstalling the console does not stop the job or delete databases. The uninstaller warns about this and also preserves the local password-free connection profile.

  1. If removing only the console from a computer, uninstall through Windows Settings → Apps. The engine keeps running.
  2. To stop the entire product, first click Pause automation and verify a PAUSED execution.
  3. IT can disable the selected job after confirming pause. Retain backups and history under the customer's policy.
  4. Uninstall the console. Permanent database/object deletion requires a separate DBA decision; Setup does not perform it.

From Settings → Export diagnostics, save the support JSON. It includes product version, database/server and engine state; it excludes passwords, customer registration and free-text audit content. Review it before sharing: server/database names are still internal information.

Provide the package version, SQL/GP builds, failed step, UTC date/time and an error screenshot without secrets. For engine issues, IT should also review Agent job history and the console's Activity.

Customer registration does not activate or deactivate the software. The acquired version continues working without maintenance renewal. The repository's MIT license is preserved.
